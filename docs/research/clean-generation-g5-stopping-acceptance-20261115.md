2026-11-15（Asia/Tokyo）。主仓库 `main`，基于已有未提交成果。

## 收尾判断

**G5 可以结束本轮工程阶段，进入 Git 收尾审阅。** 该判断限于现有 S0/BGE、官方
`deepseek-flash` 和本地单用户研究链的有界工程能力，不等于全题型语义质量、G7 产品验收
或正式默认入口采用。没有实施 G6/G7，也没有自动提交、推送或切换入口。

实际取得：两次核心证据充分后的模型 `finish(sufficient)`，以及一次针对关键缺口补检后的
`finish(limited)`。前两次结束时各还余4次单轮请求；第三次处于全批最后一个研究槽，
仍由模型说明证据缺口并提出 limited，程序没有用 budget_exhausted/context_budget 代替它。
因此不把第三例夸大为“无预算压力也必然同样停止”，但其有限结论和未知边界是正确的。

用户本轮最多10次新请求，**实际10次、10 attempts、零重试、零 UNKNOWN、零扩额**，已全部关闭。
后续提出的“如不足可再批准6次”没有启用、没有增加 permit 或产生请求。
真实自纠错按用户最新要求是非阻断项；本轮恰有两次自然发生的格式纠正，没有诱导错误或额外协议探针。

## 小范围实施

配置 `gc-g5-official-4` / `evidence-value-1` 复用原控制器、工具、LangGraph、Assembly、
G3 shared caller 和 G4 会话/UI，没有新依赖、模型、团队或知识层。

1. 初始和每次工具反馈给出 decision_feedback：已检查的缺口、最近行动、新增 receipt/
   fragment/source-item 身份、无新增回执次数和实际余量。**新身份不等于有效证据或独立印证**，
   语义收益由模型结合正文判断。
2. 现有 research_plan 可选记录 resolved/unresolved/deferred；它们是模型工作状态，
   不升格为来源事实。简单问题无需调用计划或另开“评估请求”。
3. 继续研究要说明：尚未解决的具体问题为何影响核心答案，以及查到何种材料会改变答案。
   核心充分用 sufficient；关键内容仍不可核实用 limited；没有有效增益且无更好路径用 no_gain。
   可选身份/背景旁支未解不妨碍结束，不要求穷尽全部资料或为明确原文凑反方。
4. 保留直接回答、select＋finish、重复回读提示及原文引用去重。没有降低工具/检索自由度，
   没有减少上限或增加固定规划/核验轮次。现有 hard guard 仅继续承担资源/故障保护。
5. 新增 termination.actor/method/reason/remaining，区分模型 finish、简单直接回答和程序截停。
   有限结论与预算耗尽不再仅靠最终是否有答案来混判；旧封存结果不补写新字段或改判。

来源、引用编号、原生工具参数及 reasoning 历史、持久化、UNKNOWN 规则保持原合同。
原始问题、每个子查询、候选顺序、完整回执和处置记录保留；无跨查询 logits 混排。

## 真实连续研究

运行根：`data/generation/g5-stop-live-20261115-d/`，三个 turn 属于同一 chat。
问题是正常研究请求，没有工具错误注入，也没有指示模型固定调用次数。

| 案例 | 实际动作与判断 | 请求 | 结果 |
| --- | --- | ---: | --- |
| 信物/挑战是否证明正式立约及后来解开 | 初始 S0 已含完整故事；模型排除身份、同名石锁等旁支，主动充分结束 | 3 | completed / sufficient |
| 被打断的话是否补出“解开就结婚” | 复用同 chat 范围并核验当前 Packet，确认文本没有补出，保留未知 | 3 | completed / sufficient |
| 索取实际解锁步骤 | 先识别必要缺口，执行一次聚焦 S0/BGE 补检，再选择证据并主动有限结束 | 4 | partial / limited，属于预期有限交付 |

前两例各包含一次参数纠正，故不是每题机械3次；第三例也不是模板要求4次。

### 充分时不继续研究

首例已有 content1222 武器故事，能回答用户限定的文本问题。模型没有因人物身份或无关
同名石锁继续检索，finish 时单轮还余4次请求、5次搜索、42次读取、14次工具机会。
追问也在单轮还余4次请求时 finish。两者都不是在程序最后槽位被动综合。

### 缺口重要时仍会继续，收益有限时能结束

第三例初始包主要是社区原型考据，没有可操作步骤。模型用 research_plan 明确：
已知“鲁班锁/笼中取珠”是猜测；必要未知是是否有实际解法；人物身份和其他同名锁暂缓。

它提出的补检理由包含可检验的答案变化：“若有步骤，将从原文无解法变为有步骤”。
实际增强查询为 `尘世之锁 石锁 解开 方法 机关 步骤`，kind=subquestion，parent=original，
原始口语问题没有覆盖改写。一次补检新增3个片段身份、1个 source-item，找到直接武器故事，
**但没有新增解锁步骤**。模型没有把“有新来源”误当“已经找到解法”，也没有无限改写搜索，
而是 finish(limited) 并列出构造、前提、动作顺序和机关触发方式均未知。

此例 finish 前全批只余1次综合请求（单轮尚未达6次上限），结束理由仍是材料缺失、
同类补检不再提供有效步骤，不是宣称充分解决实际解法。literal no_gain 本轮没有使用；
低收益有限结束由 limited 展示，no_gain 分支及无新增时主动停止另有离线证据。
不为凑三个枚举值重复付费测试。

第三例仍单独调用了 select，再用一次请求 finish；同批合并的提示并非每次奏效。
追问则把 finish 放在 select 之前，程序据合同跳过其后选择，没有恢复研究或执行无关动作。
这些是可优化的调用效率问题，没有形成重复检索循环或故障伪装成功。

## 问答与来源审阅

Codex 对最终 Packet/原文逐项复核，未修改三份模型原答案：

- 首例当前 E02/content1222 支持“信物/挑战”的原句、“没有正式的契约”的叙事和
  “许多年未能解开”。回答没有扩成永远未解，未确定无标记句子属于某人的明确心声。
- 追问 E01/content1222 的破折号及“不知道那句话的下文”支持没有补出下半句，
  不支持把婚约联想当文本事实。E02/content6849 被识别为社区转引；同名成就不是补全依据。
- 解法例 E03/content1222 没有机械构造或操作步骤；E01/E02/content6849 明确带作者个人
  原型猜测，回答区分现实玩具原型与游戏故事解法，没有拼造步骤，实际核心答案保留未知。
- 三个 turn 的引用都绑定当前 Packet/receipt/fragment，社区转引未成为独立官方印证。
  元数据和原文均可回读；同 chat 旧模型解释仅作待核验上下文。

行文仍有非阻断瑕疵：追问开头“没有任何……意思”“文本内外都未知”等措辞偏绝对，
应更稳定地限定为“当前材料没有明确表述”；末段已有未证实联想的限定。
解法例装备描述的引文来自社区转引，最好明确其来源层次，核心缺步骤判断另有直接武器故事支持。
首例对引文前后位置的概述不够精细。这些不应被说成整库/作者意图已经证伪，也不构成
对未知解法的实证。G5 工程通过不抹去这些表达质量的改进空间。

原始结果 semantic_acceptance=NOT_REVIEWED 保留；本报告是 Codex 的有界工程与来源审阅，
不是用户独立盲审、全题型接受或 Canonical 事实采用。

## 两次自然纠错与一次本地修复

首例首次 finish 把说明性中文填进 reason 枚举，严格返回 $.reason/TOOL_ARGUMENT_ENUM。
整批未执行，模型在新正常操作中改为 sufficient，再生成答案。纠正占用同一额度。

追问首次 finish 的参数不是合法 JSON，回执应为 INVALID_ARGUMENT_JSON；新收益摘要却对
解析后的 None 调用了 .get，造成 AttributeError。这是本轮引入的本地缺陷，现已加类型防护，
新增完整“坏JSON→拒绝→纠正→停止→答案”回归，并在真实原 turn 恢复后验证成功。

恢复没有重发第四次请求，也没有换根或重置预算：

1. 原模型调用完整封存，usage 已知；所有4次请求无 UNKNOWN/在途。受影响步骤是未执行的
   拒绝批次，尚无工具回执或已发布 tool unit，也没有来源写入。
2. 在数据库副本离线试验：只追加新 checkpoint 的 code 字段，确认 next 仍为 tools，
   其余 state/operation/history/来源引用完全相同，旧 checkpoint 仍可读取。
3. 原 permit 和 raw/ledger 不改；追加 code-only revision，所有额度、到期时间和渠道相同。
   另记录一份显式、一次性、无工具效果的修复证明，不向产品加入通用自动迁移器。
4. 对原 turn 显式 continue，复用已封存模型结果，先产生准确拒绝反馈，模型修复 JSON 并
   finish，再生成答案。没有重跑原 S0 查询，没有增加原调用 attempt。

`local-repair/report.json`、数据库试验副本、旧/新 checkpoint 与 revision/snapshot 保留上述证据。
此方法不得用于 UNKNOWN、在途、来源损坏或账本异常，也没有改变它们的严格停止规则。
两次纠错均自然发生，未花请求诱导犯错；真实自纠错本轮按用户要求保持非阻断。

没有证明任意额度、复杂度下的最优停止。Step-Back、复杂 thinking 和多跳的旧证据保持
