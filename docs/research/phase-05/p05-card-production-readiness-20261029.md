## 已完成的确定修复

- 新引文合同只要求模型给片段 ID 和逐字引文，程序在该已验证片段内唯一精确定位。
  缺失、异端或重复歧义拒绝，不模糊匹配；结构化/对话仍使用 RU 范围，只有富文本可
  映射 Canonical 字符范围。完整选择器、分支和来源快照保存在 job evidence。
- `source-local-attribution-v2` 仅改变位置交付方式及诊断身份，不再要求模型计数。
  历史 v1 保留原合同严格重放。对两份历史原响应去除模型位置后作独立工程重放，
  128+45 条引文均可唯一定位；**未修改旧失败结果，也未纠正其中的语义错误**。
- `p05-navi-typed-source-runner-2` 将实际请求体、完整 raw/SDK 流及合法 usage 核对，
  与输出 cap 和内容合同验收分开保存。已知用量不会因 JSON、引文或 cap 失败变 UNKNOWN。
  cap 超限仍使内容失败、禁止后续收费派发，不重试；未知发送或未知用量继续阻塞。
  重放也保留已知 usage。仅完整流可核验的数字称为 provider reported，不称账单。
- 历史反例实际 body 为 `max_output_tokens=12000`，终态上报输出 17018；正例为 4938。
  历史上报总量仍是 43117，并非本轮新增消耗。现有档案不能确定是提供商未执行上限、
  计数口径还是其他服务端问题；不能用增大本地 cap 来宣布修好提供商行为。
- 辅助核验默认关闭，仅保留可选诊断。风险标签不决定正式事实审核、v0.3准入或发布。
  不再优化其语义 Prompt，不再围绕两例调用模型。冻结 v0.3 及原账本、历史索引不变。

## 历史 Card 的实际缺陷

首轮12来源生成84个阅读批次，79份有已知用量、78份内容通过；其中24批成长数值、
8批秘境详情。文档节点的 `overview` 直接拼接各成功批次摘要，父节点的五类语义项
也直接展平；这既造成重复查询，也使“读了哪些页面组件”取代文档故事归纳。
例如破魔文档的8段摘要包含基础信息、数值、甘雨适配和图片，只有一段是故事。
曚云文档也把精炼机制与海祇叙事放在同一语义对象中。

不能把全部错误归咎于 Card：破魔历史观察已经正确记录“若教射术者未随将军出征，
孩子应是左卫门年纪”的条件句；另一条观察把当下人物与旧人相似描写压进一个句子，
指代边界不够清楚。后续 Link 在完整原文下仍归错人物，说明 Card 不能代替原文审核。
小说、圣遗物和G1任务卡已有具体事件/开放问题，不能因为文档聚合差就全部废弃。
`3429` 历史G1卡保留绘真寻找失书、搬迁前最后一天等线索，并声明不是完整任务或史证。

## Card v2 的实现

入口与职责仍在 `retrieval/navi_offline/`：`cards_v2.py` 负责新合同/阅读/投影，
`card_build.py` 只编排 Card 作业，`card_census.py` 做离线规模统计。旧 `cards.py` 和
旧完整 Card→Link 路径保持可重放；新路径不启动 Link、RU Embedding 或候选发现。

1. **内容适应阅读**：按真实章节、来源类型及正文长度安排批次，短资料直接生成文档卡。
   成长数值、推荐配装等章节不占默认剧情预算；混合装备描述只选择精确的叙事行。
   可读但未分类的正文保守保留。结构化伴随表示默认不重复交付，也不宣称它与富文本
   语义等价；无富文本的结构化叙事及对话图仍可读。每条 RU 保存已选/未读区间、原因，
   空内容、上游跳过项和 Canonical 单元清单也保留。未知关键结构隔离报错。
2. **真正归纳**：多批次章节、文档分别发起语义归纳请求，输入子卡而非拼接字符串。
   太多子卡按同一预算逐层归纳，内部节点称 synthesis batch，不冒充章节。
   合成观察只能继承子卡已有的原文引文，不能新增未交付的引文；继承与直接阅读分开，
   文档没有直接阅读全文的声明。单个子卡已超预算时明确失败，不静默删字段。
3. **事实归属**：观察项分 `subject/action/object/modality`，保留原文陈述 text 和精确
   anchors；未知主体、假设、回忆、年龄比较和分支必须保留边界。解释、假说、问题仍
   分栏且可为空，线索层从有来源的问题展开，可为零。程序只证明位置和交付，不证明
   模型对人物、行动或指代的理解正确。
4. **剧情投影**：`card_narrative_attributed_v3` 使用文档/章节归纳、具体主体行动、来源
   模态、解释、明确标成 `HYPOTHESIS_NOT_FACT` 的假说及待查问题。排除阅读回执、
   机器 ID、人工状态、旧评分和配装目录；线索卡保留，但不与父卡重复作为向量所有者。
   假说标签不能保证 Embedding 模型完全区分其真伪，需后续检索验证；任何 Card 内容均
   不能作为 Link 的原文证据。旧投影、RU检索与2048维回退索引不被替换。
5. **可恢复与定向更新**：一次来源准备校验/扫描RU，后续按资料读有界缓存；富文本
   偏移表按资料一次建立。每个请求及每份资料版本只创建一次；调用批次上限可分次推进。
   完整成功 job 可经精确输入核对重放复用；失败、UNKNOWN、pending不自动重发。
   新建 revision+reason 可定向重生成资料，或用 `--regenerate-jobs` 只重做指定作业及
   受其影响的上层归纳，其他成功阅读复用。旧原件保持不变。
6. **增量索引**：新完整 Card 版本生成新索引；`--reuse-from` 通过同模型、设备、投影及
   窗口精确身份重用向量，只编码变化窗口。用临时磁盘定位表、分片 mmap、有界批量，
   不全量加载旧向量。完成分片可恢复，失败片保留。全部来源完成前不默默发布部分索引。

## 全库成本和资源：估算，不是已发生消费

历史79次有已知用量的 Card：输入406382、输出173387 Token。输入/序列化wire字符的
加权比例0.36419、p95为0.40553；单次输出中位2257、p95为3609。用这些历史观测作代理：

| 情景（均非上界/保证） | 总请求 | 预计输入 | 预计输出 | 预计总Token |
|---|---:|---:|---:|---:|

| 归纳任务翻倍且用满24000字符、输入p95、输出1.5×历史p95 | 34592 | 203335841 | 187263792 | 390599633 |

新主体/引文字段会改变输出长度；实际归纳树、失败率和服务端计数也未知。这两种情景
不是置信区间、严格最高预算或供应商报价。收费公式为
`输入Token/百万 × 已确认输入单价 + 输出Token/百万 × 已确认输出单价`；缓存折扣仅在
有可信账单规则时单独计入。**单价、币种及全库费用 UNKNOWN，本轮新增收费0。**
未来每次派发还受真实账本和保守字节预留预算控制；全库收费授权尚未取得。

实机16GB内存、RTX3050 Laptop 4GB，观察时可用内存约1GB；本轮不再加载模型。
延用固定Qwen3-Embedding-0.6B、CUDA FP16、batch2、1024维独立空间。
21702所有者若各2—6窗口，则43404—130212行、纯FP32向量约170—509MiB。
按历史12.37行/秒只是约1—3小时编码的参考，未包含新文本token化、IO和全库检索开销。
生成若每请求60秒串行，两个情景约21.9—24.0天；它是吞吐假设，非新运行实测。

历史单个Card job归档平均约903KB；31504次按此粗估仅job就约28.45GB，另有约2.28GB
Canonical快照、全RU定位库、Card多层产物、向量及失败证据。D盘观察时仅约33.68GB
剩余，因此现有空间缺乏可靠余量。应先准备更充足的工作空间并确认忽略目录的独立备份；
同盘复制和代码提交都不构成独立备份。无需换模型，也不需全库RU重嵌入。

## 使用与下一步

PowerShell 7，仓库根目录；下列命令只准备/Mock，不读取真实凭据、不收费：

```powershell
$env:PYTHONPATH = 'src'
python -m genshin_corpus.retrieval.navi_offline card-census `
  --out data/retrieval/my-card-census
python -m genshin_corpus.retrieval.navi_offline card-prepare `
  --run data/retrieval/my-card-preparation --sources 2287 3076 3866 4275 3429
python -m genshin_corpus.retrieval.navi_offline card-run `
  --run data/retrieval/my-card-preparation --backend mock --max-new-requests 20
python -m genshin_corpus.retrieval.navi_offline card-resume `
  --run data/retrieval/my-card-preparation --backend mock --max-new-requests 20
python -m genshin_corpus.retrieval.navi_offline card-audit `
  --run data/retrieval/my-card-preparation
```

`card-prepare` 不给 `--sources` 时准备整个 Canonical；它会复制来源快照并建立定位库，
不是开始收费生成。`card-index` 是显式单独命令，使用新目录、`--reuse-from` 可复用
同合同的旧窗口；本轮不执行大规模编码。不要把 Mock Card 索引用于真实语义结论。
定向再生示例：新准备目录中指定 `--sources <资料ID> --revision <新版本> --reason <原因>
--regenerate-jobs <旧job_id>`，运行时 `--reuse <旧Card运行目录>`；只重做该作业及依赖归纳。
不指定作业则重做所选资料版本。任何 live 模式都还需独立授权、精确计划摘要及总预算。

建议最小真实验证为**5来源**：破魔、曚云、来歆余响、暮夜剧团团长的手稿、龙蛇藏归辑录。
已知阅读1+1+1+6+1=10次，至少另1次文档归纳；初次授权可限**最多12次实际发送**、
无重试且不扩样，额外归纳不足时保存延期。仅Card，不调用Link/辅助核验、不嵌入全库。
检查人物行动、分支、假说模态、文档归纳和有效信息密度，并用原件确认cap/usage行为。
这仍不能证明全库质量，之后才决定分批生产规模与预算。**本轮未执行这些收费请求。**

完整证据根：`data/retrieval/p05-card-production-readiness-20261029-r1/`。
历史原件、索引及冻结引擎的236份保护文件哈希保持不变；独立备份仍未确认。
