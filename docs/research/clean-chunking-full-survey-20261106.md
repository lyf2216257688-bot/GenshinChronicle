# Clean 全量数据与分片方法调查

调查日期为 2026-11-06。本文记录全量结构统计、实际文本观察和方案候选，供新版 RAG 分片讨论使用。候选的命名、数量、准入规则及长度参数均有待商议。

## 1. 调查结论与建议起点

本次以 `clean-v1-full-20261106` 的 **16,437 条 Clean 记录**为调查总体，逐文件读取并核对清单 SHA-256，覆盖 **84,072 个模块、30 种组件、5,087 组对话、60,682 个节点和 62,727 条边**。另检查了同目录下的 30 条试点记录与全量 run 的关系。定向阅读形成 **27 个结构案例、22 条记录、68 段带 CleanRef 的原文摘录**。全量扫描覆盖结构，定向阅读用于解释结构的实际用途。[全量统计](../../data/retrieval/clean-chunking-survey-20261106/summary.json)、[调查范围](../../data/retrieval/clean-chunking-survey-20261106/scope.json)、[实际文本样本](../../data/retrieval/clean-chunking-survey-20261106/examples.md)

建议优先讨论 **一套通用的结构分片核心，配少量结构输入适配**。

- 正文、书籍、角色故事、富文本任务对白等，可以共用“原始容器内按顺序组合，超过上限再递归拆长”的核心。
- 字段、语音条目和表格先恢复条目及键值关系，再使用同一套组合、拆长规则。所需差异主要在文本组装和保护边界。
- 结构化对话先组织共同流程、选项集合、局部回应及公共后续，再使用共同的长度规则。图关系承担原文连接和回读定位。
- 混合页面可以逐模块、逐字段采用上述处理。角色、任务、书籍、武器、材料、地区等业务栏目可以作为准入和上下文信息。

若需要先给处理候选命名，可以暂列 **结构文本组装**和 **对话组装**两项。字段及表格适配的工程复杂度若在后续讨论中明显增大，可再把“条目成组”单列为第三项。当前数据支持先共用核心、再按实际难点细分。

本报告采用用户补充的剧情前提。**总体剧情按线性流程理解，普通选项主要改变表达和局部回应，少数任务完成先后会改变细节。** 因此，建议合并公共后续、保留不同选项和条件台词，将局部变体归在同一剧情父层下。森林书的条件差异在真实 Clean 中也有直接记录，见第 5.4 节。

当前 Clean 已提供纯规则分片所需的大部分结构。主要工程工作集中在 **内容准入、文本投影、原始容器边界、对话及条件标签的组装、来源引用**。检索精度的实际改善仍需要后续使用少量问题和原文进行对照，本轮统计仅用于确定方案讨论范围。

### 2.2 调查步骤

1. 阅读仓库当前阶段、Clean V1 合同、实现记录、Raw 结构调查和架构边界。
2. 阅读交接入口、现状快照、六分支接口索引及技术决策总账的相关章节。
3. 遍历全量记录，核对记录文件哈希和身份，统计栏目、标签、模块、组件、字段、结构块、长度、图关系及诊断。
4. 按结构差异、长度尾部和筛选误伤风险选择实际文本。样本同时覆盖常见结构和容易误判的载体。
5. 对照本地教程 P05、P10、P30，并核对递归切分及父子检索的上游文档，分析技术适用范围。
6. 将事实统计、样本解释、方案建议和待商议取舍分开记录。

程序仅生成调查统计、样本和报告。全量文件哈希核对确认本次统计绑定的 Clean 文件，完整 Raw 保真复核属于独立验收。原文样本通过现有 `iter_blocks / iter_text_values / CleanRef / resolve_clean_ref` 接口提取和检查，使用的来源粒度以 Clean 合同为准。[Clean V1 合同](../phases/clean-v1.md)、[调查程序](../../data/retrieval/clean-chunking-survey-20261106/survey_clean.py)、[样本提取程序](../../data/retrieval/clean-chunking-survey-20261106/review_examples.py)

### 2.3 长度与字段统计的口径

- 所有长度均为 **Unicode 码点数**，使用 Python `len`。Embedding tokenizer 的 token 数需要在索引方案选定后另行计算。
- “组件正文投影”提取 `component.blocks` 中实际 TextValue，按换行连接，排除字段标签、组标题、source_fields、标签和 scalar 的数字字面。投影中仍包含音频文件名等待下游筛选的字符串。
- 标题、字段标签、数字、媒体、关系和源控制字段通过其各自结构保留。本报告的正文投影字符数用于比较结构尺寸，不能解释为最终剧情检索文本总量。
- 表格正文包含其单元格文本。语音组件的表格型数据还表现为有标题的 group 和 field，另有条目统计。
- 同一字段父容器及其子字段分别统计。字段目录中的子树字符量存在包含关系，不能直接相加。
- 栏目统计按记录实际 membership 去重。父栏目和子栏目可以同时计入，同一记录可有多个归属。
- P50/P90/P99 为排序后的描述性分位点。扫描保存了完整目录和逐记录尺寸，便于改变统计口径后重算。

### 3.4 组件和机器字段的结构能力

高频组件包括 `collapse_panel` 33,974 个、`map_desc` 9,920 个、`material_base_info` 7,435 个、`rich_base_info` 5,022 个、`interactive_dialogue` 5,002 个、`good_desc` 3,322 个、`multi_table` 2,009 个。各自出现次数及涉及页面数均保存在完整目录中。[30 种组件目录](../../data/retrieval/clean-chunking-survey-20261106/components.json)

三个事实尤其影响规则设计。

1. `collapse_panel` 同时承载角色故事、书籍、富文本对白、攻略、任务奖励和空模块。可复用其读取和段落组合方法，准入需结合模块用途。

3. 同一个模块名对应多种源结构。“剧情对话”共2,312个模块，其中1,565个为 `interactive_dialogue`、747个为 `collapse_panel`。“NPC对话”共2,868个模块，其中2,215个为前者、653个为后者。两类载体可以共用部分文本规则，结构读取需分别适配。

这支持有限的结构适配和配置式字段选择。为每种角色、地区或故事主题编写分片器，会把大量相同处理方式重复实现。[字段目录](../../data/retrieval/clean-chunking-survey-20261106/fields.json)、[模块统计](../../data/retrieval/clean-chunking-survey-20261106/sections.json)、[组合统计](../../data/retrieval/clean-chunking-survey-20261106/analysis.json)

### 4.2 对处理方法的直接影响

- **相邻短内容组合将比超长单段递归更常见。** 非空 HTML 段落中位数17字符，很多段落是短句、台词和单行项目。模块中有40,244个非空正文投影不超过200字符。可以在同一章节、字段条目或对话局部组合相邻内容。
- **短内容可自然独立。** “卡牌故事”701个模块合计23,534个投影字符。附带文档和条目名后，完整的短文本本身就可能具有检索价值。最低长度宜作为软目标。
- **整章保留和超长拆分需要并存。** 单模块超过1,200字符的有2,635个，超过8,000字符的有442个。长书卷和大型任务对白需要在章节内部继续分组。
- **长对话节点也需要拆长入口。** 一个源节点可承载多轮台词和长篇文章，节点最大15,898字符。拆分可保持节点身份，并让子片段回指该节点的不同文本范围。
- **正文为空需要看资源结构。** 32,451个模块的本次文字投影为零，包含图片、视频、空占位等来源。媒体和文字状态宜分别记录。

因此，适合让结构边界控制优先级，让尺寸限制处理尾部。先建立完整父容器，再按需要形成可检索子片段，能够同时支持精确匹配和后续回读。[补充统计](../../data/retrieval/clean-chunking-survey-20261106/analysis.json)

### 5.1 连续叙事和书籍可共用有序组合

- 普通表达选项可以成组展示，公共后续按来源关系复用。

## 6. 尽量精简的处理候选

### 6.1 共用的结构分片核心

建议先用一套确定性过程承担共同工作。

1. 根据源栏目、标签、模块及字段规则选择候选内容，并保存选择理由。
2. 恢复文档、模块、局部标题、条目、表格行或对话局部组等原始容器。
3. 容器内按原文顺序组合相邻短内容，保留完整段落、条目和局部回应。
4. 对超过限制的容器逐层使用子结构、段落、行和句子边界继续拆分。
5. 保存父容器引用、片段来源、原顺序及必要的标题上下文。

这套过程可以容纳不同长度的自然单元。短成品条目可以独立，长书卷和长对话局部可以拆长。硬长度约束最终需要结合实际 Embedding 输入和下游回读预算讨论。

### 6.2 两项可讨论的处理候选

| 候选 | 适用范围 | 需要保留的主要边界 | 适用技术 | 工程难点 |
| --- | --- | --- | --- | --- |
| 结构文本组装 | 连续叙事、书籍、角色故事、富文本任务对白、物品背景、字段条目、文字表格 | 模块、局部标题、条目、键值、行与列关系 | 结构感知组合、超长递归、按容器自适应、父子关系 | 表格和字段如何投影，空标题补上下文，源布局与源数组顺序 |
| 对话组装 | 有 nodes/edges 的任务及NPC对白、普通表达选项、局部完成条件、菜单式交互条目 | 对话组、源节点、选项与回应、条件原文、公共后续 | 基于已保存连接的分组，再复用相同组合与拆长核心 | option 的用途混合、长节点、缺根和孤立节点、局部条件范围 |

两个候选共享长度策略和来源表示，差异集中于组装。对话原文若已是富文本顺序表示，可以直接使用结构文本处理。结构化图中明确的单链也可以直接提供有序输入。

字段、表格和语音的适配宜优先作为输入配置与小型投影规则。例如，人物基础资料保持字段名和值，语音保持条目名和台词，故事表格保持页签与文字列。只在这些适配确实需要独立的成组策略时，再讨论将其单列为第三类。

### 6.3 父层与跨模块例外

父层建议尽量对应 **自然章节或局部内容容器**。书籍一卷、角色一个故事、武器相关故事、表格一个条目、对话一段共同流程，都可以成为候选。大型任务页最大投影268,121字符，整个页面作为统一回读父层容易夹入不相关段落。

默认维持模块和章节边界。跨模块例外可以先限于有明确来源依据的情形，例如同一布局组内的卷介绍与卷正文、同一任务局部组的源标题与相邻内容。也可以仅建立可回读关联，从而保留模块独立性。具体例外需由实际样本和布局关系支持。

一个页面可以由多个父容器构成。标题相同、文字相同或内容相邻，都需要结合原始条目、布局和引用判断其归属。父子关系和共用上下文可以减少为了凑长度而跨章节拼接的需求。

## 7. 剧情准入与误排除控制

### 7.1 建议的准入讨论表

| 状态候选 | 可以利用的结构依据 | 处理建议 |
| --- | --- | --- |
| 优先纳入 | 已知书卷正文、角色故事及自定义故事、剧情/NPC/交互正文、武器故事、圣遗物故事、地图文章、物品背景描述 | 形成原文容器，并附来源和局部标题 |
| 明确机制内容 | 属性与成长数值、培养材料数量、奖励数量、商店价格和库存、配装推荐、明确的战斗参数表 | 在剧情检索派生物中记明未纳入的字段和理由 |
| 混合或边界不清 | 技能desc、教程文字说明、成就补充、用途字段、空标题富文本、含故事的外观描述 | 保守保留，使用原始模块和字段上下文，后续定向讨论 |
| 来源性质待确认 | 考据文章、汇编、带可见署名的解释性内容 | 携带原始来源证据，商议独立检索范围或展示策略 |
| 资源型 | 图片、视频、音频、外链、无正文占位 | 保留资源关联和可见文字，按可用内容决定检索表示 |

表格表达的是调查后的候选边界，最终准入集合尚未冻结。机制字段中嵌套可见背景文字时，应保留其局部故事入口。

### 7.2 规则优先级

建议让明确的故事证据拥有局部保留入口。例如，卡牌页的“卡牌故事”可以单独纳入，武器页的“相关故事”可以单独纳入，洞天和背包的背景段落可以单独纳入。之后再在其余字段中处理明确机制、资源控制信息及边界混合内容。

机器规则宜采用 **栏目 + 模块/组件 + 字段键/原标签 + 作用域** 的组合。`source_filter` 的“任务类型”“类型”等键需要保留各自的实际赋值，`content_role` 的有限覆盖可以作为高精度入口。文档标题、源别名和章节标题也可用于检索上下文，跨文档身份统一需要独立依据。

选项和条件应分别保留原文用途。“非常顺手”和“马马虎虎”可作为共同询问下的表达选项，“完成……”与“未完成……”作为明示条件文字。两种局部组都可绑定同一个剧情父层，并保持源节点身份。

### 7.3 派生记录所需的最少信息

在后续分片合同讨论中，建议保留内容选择理由、Clean run/manifest绑定、observation_id、多条 CleanRef、父容器、局部顺序以及源栏目和条件原文。标题前缀、字段名和“条件”等展示上下文需要能说明生成依据。这样可以随时调整准入规则并回读原文。

Clean 完整内容和源定位继续由其现有合同负责。实际检索文本可以根据用途投影，所有纳入、暂缓和明确略过的决定可以保留在轻量派生清单中。无需为本轮调查建立复杂的验证平台。[Clean 引用合同](../phases/clean-v1.md)

## 8. 分片技术在本数据上的适用性

| 技术 | 在真实 Clean 上的用途 | 建议的使用边界 |

| 相邻窗口或重叠 | 补足跨片段的代词、询问和回应关系 | 可优先考虑相邻完整段落、完整局部回应及父层回读 |
| 向量语义分片 | 针对结构很差的少量材料，未来可单独讨论 | 当前先利用已有结构，避免新增常规语义模型依赖 |
| LLM/Agent 分片 | 特殊研究候选 | 本轮的规则调查已能覆盖主要结构组织需求 |

本地教程 P05 说明章节、段落和上下文的关系，P10 介绍结构感知、混合拆分、父子块和重叠，P30 展示递归及中文分隔符。这些方法可借鉴其机制，具体500/50等示例参数需要依据 GC 的短段落分布和局部剧情结构重新商议。[P05 分片](D:/RAG教程/docs/01_RAG核心原理与基础/P05【05.分片】.md)、[P10 高质量文本分块](D:/RAG教程/docs/01_RAG核心原理与基础/P10【10.高质量文本分块实战指南】.md)、[P30 文档切分](D:/RAG教程/docs/03_LangChain_RAG实战组件/P30【30.LangchainV1.2最新版-RAG实战-文档切分document_splitter】.md)

递归字符切分按分隔符优先级及长度函数工作。中文需要显式考虑句号、问号、叹号等边界，句子和引号是否完整还取决于具体规则。教程示例中的空格、换行和字符兜底，可以作为机制说明，正式规则需优先利用已有段落及容器。[LangChain 递归切分文档](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)

父子检索将小片段的匹配与较大父层的返回分开。GC 可以先保存这类关系，让重排与生成分支讨论回读粒度及证据预算。父层可对应较大的局部块，具体框架依赖和索引方案可以后续再选。[LangChain ParentDocumentRetriever 源码](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/retrievers/parent_document_retriever.py)

本轮没有根据长度统计预设最优字符数。若下一轮需要少量候选尺寸，可从短条目、普通章节和长对白各取实际样本，以中文字符作为展示尺度，同时测实际模型 token 数，再讨论软目标与硬上限。尺寸和重叠可以共用少量参数，章节和条目边界仍拥有优先级。

## 9. 当前 Clean 的支撑能力与工程难点

### 9.1 已有能力

Clean 已提供模块及组件源顺序、布局观察、字段键及原标签、原段落和局部标题、表格行列与跨度、对话根节点和有序边、资源与关系池、标签作用域、版本化来源定位。多个来源片段组合时，也可以通过多个 CleanRef 保持回引。

这些能力足以让常规分片采用确定性结构规则。有限的章节/字段准入配置和结构适配器有望覆盖主要处理需求。素材中的文学主题、人物身份和隐含因果可以交给后续检索与分析使用。

### 9.2 对话结构的实际复杂度

| 观察项 | 对话组数 / 节点或边总数 | 工程含义 |
| --- | ---: | --- |
| 至少有一个分叉的组 | 3,462组，68.06% | 选项或条目分组是常见结构 |
| 至少有一个多父节点的组 | 2,370组，46.59% | 公共后续应允许被多个上文引用 |
| 至少有不可从根到达节点的组 | 1,812组，共7,759节点 | 需要为这些原文保留独立处理入口 |
| 至少有孤立节点的组 | 2,505组，共7,042节点 | 含单节点等正常结构，需结合上下文解释 |
| 根无效或未找到 | 298组，其中237组为空组 | 有内容的缺根组需保守读取 |
| 悬空边 | 61组，共146边 | 保留异常和原文，组装时标明边界 |
| 本次检测到有向环 | 0组 | 当前可按无环关系组织局部流程 |
| 所有节点具有显式 speaker 的数量 | 0 | 原文称谓和实际字段继续分开保存 |

这些都是结构统计，**分叉和汇合用于确定选项、局部回应及公共后续的来源连接**。按照用户的剧情前提，可以围绕共同流程组装内容，并保留少数条件细节，工程上无需枚举所有完整剧情路径。[逐组统计](../../data/retrieval/clean-chunking-survey-20261106/dialogue_groups.json)、[补充统计](../../data/retrieval/clean-chunking-survey-20261106/analysis.json)

### 9.3 特殊情况和未确定事项

| 情况 | 本轮证据 | 建议 |
| --- | --- | --- |
| 空标题和源数组顺序不同于布局顺序 | 19,777个空标题模块，书卷有明确实例 | 保留两种顺序和布局依据，先建立局部容器 |
| 机器字段复用 | story、desc、materials等有不同原标签和栏目用途 | 使用组合条件，保留未知项入口 |
| 选项字段承载条件 | 森林书完成与未完成条件写在option | 保存条件原文、对应节点和来源关系 |
| 条件缺少独立机器字段 | 观察到的对话节点主要字段为dialogue、option、icon | 先保留原文条件和局部组，复杂世界状态解释待具体需要 |
| 富文本带编辑说明或选择标记 | 5778的下划线、斜体说明 | 保留marks与说明，逐源核对稳定用途 |
| 媒体中的信息 | 多个模块无文字投影，有资源引用 | 记录可见文字和资源可用状态 |
| 特殊HTML载荷 | `PRESERVED_HTML_PAYLOAD` 2,432次，涉及243条记录 | 作为定向检查入口，核对可见文本与保留载荷的用途 |
| 标签多值 | `FILTER_MULTIPLE_VALUES` 1,663次，涉及1,543条记录 | 作为多值事实保留，结合作用域判断 |
| 条目目标冲突 | `ENTRY_TARGET_CONFLICT` 270次，涉及256条记录 | 限定自动上下文关联的依据 |
| 来源性质不明 | 全量provenance为unknown | 使用可追溯原始证据，待商议检索范围 |

诊断目录提供调查入口。诊断出现本身需要结合具体源结构解释，尤其是多值标签、孤立节点和空组。[完整诊断统计](../../data/retrieval/clean-chunking-survey-20261106/diagnostics.json)

另有一项可复核的确定性问题。试点与全量中的 **509671具有相同observation_id，但record_sha256不同**。逐顶层字段比较发现差异仅在 `diagnostics` 数组，诊断多重集合相同，孤立节点诊断的排列顺序不同，其余正文、结构和来源字段一致。后续工程可检查诊断排序；本次统计绑定全量run及其manifest哈希，样本也保存各自记录哈希。[跨run核对](../../data/retrieval/clean-chunking-survey-20261106/scope.json)

### 9.4 本轮证据的限度

全量统计覆盖本地这一个中文Raw快照所生成的Clean版本。定向文本样本用于识别处理需求，内容准入的语义边界仍有待讨论。完整Raw文本保真、实际召回质量和最终回答质量各有独立评价责任。

目前能够明确建议的是结构利用方式、候选处理合并方向和需要保留的原文关系。最终最优长度、重叠、父层尺寸、索引字段和源类型权重，仍需要结合后续实际使用决定。

## 10. 需要进一步商议的取舍

| 议题 | 可选取舍 | 本次建议起点 |
| --- | --- | --- |
| 处理类型命名 | 一个通用核心配结构适配，或把条目/表格单列 | 先共用核心，以结构文本和对话组装作两项讨论候选 |

| 重叠和回读 | 字符重叠、相邻完整段落、父层回读 | 优先讨论结构单位重叠和父层回读 |

| 教程、成就、千星奇域等 | 仅取明确背景字段，或较宽保留后再缩范围 | 根据已找到的背景实例保留局部入口 |
| 跨模块组合 | 保持独立、仅建立关联、按布局组实际组合 | 默认独立，有明确来源关系时讨论例外 |
| 重复文本 | 保留全部检索表示、同源聚合、多引用共享表示 | 先从同记录同条目精确相同文本讨论，保留出现身份 |
