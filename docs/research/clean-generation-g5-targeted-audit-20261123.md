2026-11-23。针对第二批 `gc-g5-official-5` 的三次续轮 UNKNOWN、关键原文未被读用和已观察到的上下文开销。输入为上一轮四题配对封存、G7 70 题、少量 G6 对照及现行 Generation 和本地聊天合同。所有模型运行、回答、证据回执与占额沿用原档案。本次付费派发和历史 UNKNOWN 重派均为 0。 [第二批报告](clean-generation-g5-evidence-evaluation-20261123.md) · [当前阶段](../current-phase.md)

## 实施计划

1. 按共享调用账本逐次对齐请求清单、原始字节、响应和操作状态，比较三次失败与 Q068 成功续轮，用本机 urllib 和可控响应复验边界。
2. 按候选排名、预览、模型动作、回读回执、正文展示、Packet、引用和结论逐项定位损失。修复已观察到的重复传输和证据准入回退，固定语料、S0、BGE 排序和模型配置。
3. 分别计算已知供应商 Token、本机请求字节、历史耗时、局部 Python 成本及离线反事实。运行 Generation、账本恢复和本地聊天回归，给出有限真实配对的工程门槛和仍待验证的语义门槛。
4. 按补充要求回查 Q068 从正式原始观测到 Clean、Chunk、物理索引、各召回通道、融合、重排和生成的身份与排名。固定候选、原文和已选模型，离线比较排名融合、前排配额及证据意图重评分。用独立时段、条件和身份话题对照，判断是否适合改变正式排序。

三次失败均在 5.008–5.010 秒结束，首个请求均通过协议核验，失败侧也通过派发前请求校验。原请求清单均配置 300 秒。在运行所用的 Windows CPython 3.14.5 中，urllib 默认处理器在 `h.request(...)` 捕获并以 `URLError` 包装 `OSError`，该调用涵盖延迟建立的 DNS、TCP、TLS 及头部、正文发送，外部的 `h.getresponse()` 读取响应头。三次异常范围因此缩小至建立连接或发送请求阶段。旧回执没有底层原因及系统错误码，无法再定位具体阶段，也无法判定远端是否收到或执行。项目每次新建 opener，并由 urllib 使用 `Connection: close`。Q068 成功续轮和 192,274 B 成功综合说明现有证据不支持归因于第二轮固定限制或失败样本尺寸范围内的通用正文上限。 [逐次账本和字节](../../data/generation/g5-evidence-followup-cost-20261123-r05/report.json)

G7 的 14 次同类失败均已逐一核验尝试封存。它们出现在第 1、2、3、6 个请求，耗时 5.006–22.058 秒，请求体 35,766–191,766 B，清单均配置 300 秒。这类故障早于试验目录策略。历史档案也只记录外层异常，无法证明与此次为同一具体网络故障。 [G7 核验提取](../../data/generation/g5-evidence-targeted-audit-20261123/g7-transport.json) · [G7 原审计](clean-generation-g7-70q-quality-audit-20261117.md)
