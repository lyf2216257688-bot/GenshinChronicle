## 审计结论

GC 已能把研究者的问题带回具体的中文原文。用本机真实索引询问阿米尔如何描述同一位小姑娘，排在前两位的材料正好对应任务前、后两个分支，进入证据包后仍可辨认各自的条件。对于关系、身份和多问合一的问题，最需要改善的是**已经找到的资料能否被选读、读到的原句能否逐段复核、最终判断有没有回答全部所问**。已有材料足以定位这三个环节，暂时缺少全面更换召回模型的依据。

本轮确认十项实现或数据问题。按使用场景，优先处理三组。

| 使用场景 | 最先要处理的事 | 判断依据 |
| --- | --- | --- |
| 准备更新语料 | 固定已完成 Raw 批次的清单和响应，区分“指定范围处理完毕”和“全量发现、采集完毕” | 零请求续跑已足以改变清单哈希。两个条目的夹具只取一个也会报告完整，选不中栏目时连 Clean 都能产出完整的空清单。见 F01、F02。 |

| 持续几天讨论同一问题 | 按消息应用纠正，把长期历史和本轮上下文预算分开，修复本地检索中断后的显式恢复 | 实际产品接口中，只纠正助手会一并遮住用户原问题。另以临时目录复现了越积越大的历史索引和无法完成的本地重试。见 F06、F07、F08。 |

## 业务流程与核查边界

### 真实链路抽查

问题为“阿米尔提到的那个小姑娘，在完成魔神任务第三章第五幕前后有什么变化？”使用选定的本机 S0、真实 BGE 重排和现用证据读取器，在临时输出根运行。得到 100 个有序候选，读取前 6 个。针对每个候选的首个正文片段，用绑定的 CleanRef 和该记录对应的 Raw run 复核原文。随后用 60,000 的上下文预算和 4,096 的输出预留做简化组包，预算按实现的保守 UTF-8 字节估算。

结果入包 3 个片段，3 个因预算排除，94 个未选读。E01 和 E02 均来自条目 5095，分别保留“第五幕前”的养病叙述和“第五幕后”的大病初愈叙述。E03 来自另一角色拉米兹，虽有相近时间条件，却不足以回答阿米尔的问题。编号校验通过。整次抽查约 160 秒，含读取器初始化、实际推理及额外 Raw 复核。这是一次来源和条件保真的正例，也说明模型仍需分辨旁支材料。抽查止于 Packet，未生成远程答案。[本地检索与重排入口](../../src/genshin_corpus/retrieval/clean_based/runtime_v2.py#L100) · [CleanRef 回读](../../src/genshin_corpus/clean/reader.py#L307) · [证据组装](../../src/genshin_corpus/generation/clean_evidence.py#L154)

## 确定的问题

以下条目给出触发条件、观察结果和建议验收。P1 表示会妨碍对应场景的证据保存、查证或继续使用。P2 表示材料仍可找回，但通常需要额外操作或容易误读。优先级按受影响场景评定。Raw 更新问题和已封存档案问题可以独立安排。

### F01 · P1　同一 Raw 批次续跑会改变下游绑定，恢复时还可能覆盖原始响应

用包含两条详情的离线传输完成 Raw 和 Clean，再用完全相同的参数和 run ID 运行采集器。第二次传输调用为 **0**，所有响应字节哈希相同，Raw 清单哈希却变了。随后用同一 Clean run ID 再执行构建，输入绑定检查报 `Clean run ID already binds different inputs or versions`。采集器构造时就写一份带新起始时间的空清单，结束时再写结束时间，Clean 恰好绑定了整个清单的哈希。

另一次试验仅移走临时详情的元数据侧文件，原响应字节仍完整。模拟来源后来返回了不同内容，一次重取就用新正文替换了同一历史路径。既有测试验证了损坏后会重取，未约束原响应必须有独立保存的位置。当前正式 Raw 清单仍与正式 Clean 绑定吻合，本轮覆盖发生在夹具中。[采集器初始化及恢复](../../src/genshin_corpus/collector/collector.py#L45) · [Raw 响应写入](../../src/genshin_corpus/collector/storage.py#L70) · [Clean 输入绑定](../../src/genshin_corpus/clean/pipeline.py#L284) · [原恢复测试](../../tests/collector/test_collector.py#L124)

**建议验收。** 已完成 run 的正常重开复用原清单，字节和哈希保持一致，旧 Clean 可继续验证。侧文件损坏时先保留现存响应，另写修复记录或新观测。模拟中断、侧文件缺失及来源已经改版三种情形，旧字节均可按原身份找回。

### F02 · P1　Raw 的完成状态混合了运行范围、传输成功和业务成功

对已核实格式的栏目树和两条目录项，分别改变一个输入。下表是两个真实管道入口在本轮夹具中的输出。

| 夹具变化 | Raw 输出 | Clean 后续行为 |
| --- | --- | --- |
| 限制只取 1 条详情 | 预期 2、成功 1、失败 0，状态 `complete` | 全量方式读取时，1 条完成、1 条完整性阻断 |
| 指定树中不存在的栏目 | 识别到 1 个栏目，实际取 0 个列表、0 条详情，状态 `complete` | 产出 `complete` 的 0 条清单 |
| 两个详情均为 HTTP 200，响应内 `retcode=-1` | 成功详情 2，状态 `complete` | 两条详情均被阻断 |
| 列表为 HTTP 200，响应内 `retcode=-1` | 列表成功 1、目录项 0，状态 `complete` | 拒绝读取发现响应，报 `Discovery envelope invalid` |

有限采样有正当用途。问题在于只消费 `status` 和成功计数的下游，无法据此判断覆盖范围是否足以晋级，业务错误还会被当作有效缓存复用。**建议验收。** 分别记录请求范围、实际匹配栏目、HTTP 响应已保存、业务信封有效、全量覆盖成立。保留错误原始字节。上述四例都应给出可解释的不同结果，全量入口能在生成空库或逐条做无效工作之前识别原因。[列表处理](../../src/genshin_corpus/collector/collector.py#L214) · [详情与完成判定](../../src/genshin_corpus/collector/collector.py#L318) · [Clean 输入校验](../../src/genshin_corpus/clean/pipeline.py#L42)

### F03 · P1　读取结构化父级时，模型可见正文和逐段可查证范围不一致

`read_source(scope="parent")` 把父级全部 `units` 交给证据投影。生成回执的 `texts` 只解析命中 Chunk 与父级上下文，父级的其他正文没有逐一进入这个定位集合。来源面板的逐段原句和 Raw 定位取自该集合。此处的 `parent` 是分片用的结构化父级，与读取完整原始容器的 `natural_parent` 是两个分支。

在长文夹具中，父级有 83 个正文位置，回执仅覆盖 6 个，其余 77 个位置仍随父级结构进入了带 E01 的有效 Packet。复核统一按同一观测、块、值指针及字符区间能否覆盖计算，字面相同的另一处不算覆盖。再核对 G7 最终来源记录中的 5 份 `parent` 回执，Q050 条目 505415 的 120 个正文位置中缺 100 个，Q070 条目 503853 的 315 个中缺 309 个。另外 3 份在这个检查中均无缺口。G7 已发布的 120 处引文全部指向 Chunk，上述两份父级回执未入其最终 Packet。能定位到父级文件与能从引用界面逐段核读是两项不同的能力。[读取分支和模型投影](../../src/genshin_corpus/generation/clean_evidence.py#L79) · [来源面板的数据组装](../../src/genshin_corpus/local_chat/presentation.py#L174) · [Q070 来源记录](../../data/generation/g7-70q-baseline-20261117/records/Q070/evidence.json)

**建议验收。** 对模型实际可见的每个父级正文范围生成可回读凭据，或在入包前缩小到已验证的整段。用多个不同原句、同文异处和任务条件分支测试，逐段比对模型原文、面板文本与 CleanRef。任一正文找不到定位时，记录缺口并阻止该范围作为已核验引文发布。

### F04 · P1　首轮查证目录只列已读材料，模型无法直接点选排在后面的候选

逐条解开 G7 的初次请求预览，将实际发送的 `catalog` 与同轮已登记的来源句柄比对。**70/70 题首条消息都只给了 6 个句柄**。其中 66 题已登记 100 个，其余四题分别登记 83、90、94、96 个。初始化调用检索后，另用已读回执构造首条目录。后续部分工具反馈最多附带 20 个句柄，目录没有对原排名分页选读的操作。因此，“需要再核对一个已召回条目”有时要先消耗一次工具交互或重新搜索。仅提高候选上限不会解决首条消息的可发现性。

历史复核中，Q068 的角色语音在不同查询的重排结果中位列 43、9、21，均未被读取。可以固定这三个历史排名，单独测量展示标题后模型能否主动选到这条语音。[首轮检索和目录构建](../../src/genshin_corpus/rag/clean_research.py#L390) · [工具反馈和句柄上限](../../src/genshin_corpus/rag/clean_research.py#L342) · [Q068 原文复核](../research/clean-generation-g7-70q-quality-audit-20261117.md)

**建议验收。** 给已排序的同一候选集提供可分页的标题、出处、条件和句柄，小预算内允许按原顺序取下一页。读取仍须校验同轮身份。固定召回、排序和原有阅读预算，比较支持目标结论的原文进入 Packet 的比例、补查次数与实际耗时。

### F05 · P2　首轮直接作答可以有有效引文，却没有可展开的父级原文

G5 在最终综合路径上读取已入包证据的自然父级。首轮直接作答可以绕过这一步，产品查证只读取已经保存的父级回执。重新从 G7 最终答案反查，55 份里有 48 份带绑定引文，合计 120 个“轮次、Packet、E 编号”地址。逐一核对引用的阅读回执哈希，发现 **4 份答复、11 处引文没有已保存父级**。这四份全是首轮直接作答，分别为 Q009、Q025、Q038、Q055。其片段引用仍可核验，页面也如实提示父级尚未保存。[直接作答和最终综合](../../src/genshin_corpus/rag/clean_research.py#L430) · [父级引用回读](../../src/genshin_corpus/rag/clean_conversation_graph.py#L98) · [面板提示](../../frontend/src/components/EvidencePanel.vue#L30)

**建议验收。** 对同一来源分别触发直接回答和最终综合，用户均能在相同观测版本上核读引文上下文。可以在发布时保存父级，或点击后按旧快照校验并补读。补读材料应标明取得时间，以及模型作答时实际看到的范围。

### F06 · P1　只纠正助手回答，会连同用户原问题里的约束一起遮住

通过临时产品实例发出“只讨论须弥，并按任务完成前、后分别列出依据。”取得 Mock 答复后，以其**助手消息 ID**为目标提交剧情纠正。下一轮上下文把该助手答复和同轮用户消息都标为 `requires_review`，两段文字均替换为“旧前提已被纠正”。用户没有撤回的地域、前后对照要求也从本轮可见的消息和研究状态中消失。原始用户消息仍在会话库里。原因是产品保存了消息级目标，上下文整理却把失效范围扩大到整个轮次。[纠正目标及依赖](../../src/genshin_corpus/local_chat/store.py#L203) · [按轮次屏蔽上下文](../../src/genshin_corpus/rag/clean_context.py#L22)

**建议验收。** 分别纠正助手陈述、用户剧情前提和用户范围要求，逐条核查下一轮模型可见文本。失效范围应能解释到目标消息和有记录的依赖。上述例子中仍能看到用户的原范围，助手的被纠正结论不再被当作可沿用前提。

### F07 · P1　单条消息的准入与上下文预算脱节，短消息累积也能让会话无法继续

产品接口和输入框允许 12,000 字符，Live 上下文整理预算实际为 24,000 UTF-8 字节。首轮输入 9,000 个常见汉字，草稿合同接受，但上下文整理在检索前报 `PROTECTED_CONTEXT_EXCEEDS_LIMIT`。第二个用例仅使用单字问答、无补充约束，每轮一问一答、按实际格式生成 64 个十六进制字符的消息 ID。150 个历史轮仍可组织，170 个历史轮时，即使删光旧摘要节选也报 `CONTEXT_INDEX_EXCEEDS_LIMIT`。原因是组织审计对象保留了全历史消息 ID，它们也占用本地字节预算。170 是该夹具的观察点，实际门槛随历史内容变化。[产品消息上限](../../src/genshin_corpus/local_chat/contract.py#L12) · [上下文预算和全量消息索引](../../src/genshin_corpus/rag/clean_context.py#L47) · [Live 预算](../../src/genshin_corpus/rag/clean_research_live.py#L70)

**建议验收。** 长题在排队前得到明确的预算反馈并保留草稿。历史全索引保存在本地，送去模型的近期对话、仍有效的约束与可回取的旧证据引用独立计量。用 200 轮短对话、中文长题和多次纠正验证，能继续追问，原始消息和旧引文仍可回查。

### F08 · P1　本地检索尚未封存就中断，同一轮显式恢复会反复失败

本地管道先创建查询目录，最后才保存 `complete.json`。G5 恢复时对任何已存在的目录直接执行完整封存验证。在临时批次中模拟“已创建原查询目录、已留下工作日志、尚无封存清单”的状态，连续两次从实际 `ResearchPipeline.run` 入口继续，两次都在查找同一份 `complete.json` 时抛出 `FileNotFoundError`。该窗口中断的是纯本地检索。修复它可以单独验证是否会引起新的远端派发。[本地管道创建工作目录](../../src/genshin_corpus/retrieval/clean_based/runtime_v2.py#L116) · [G5 复用与封存](../../src/genshin_corpus/rag/clean_research_live.py#L227) · [产品恢复入口](../../src/genshin_corpus/local_chat/api.py#L122)

**建议验收。** 隔离并保留未封存的本地尝试，为同一逻辑查询建立新的本地工作目录，或从已经核验的本地步骤继续。在“启动本地工作进程后”“写入排名后封存前”“远端请求已经占额”三个切点模拟中断。前两处可以重新完成纯本地工作，第三处继续按原操作和账本对账，UNKNOWN 不产生重复派发。

### F09 · P2　已绑定引文数为零也能记录引用校验 PASS

G5 从答复中提取形如 `[E01]` 的编号，再检查提取集合是否为 Packet 编号的子集。空集会通过。重新汇总已发布答复，G7 有 **7 份**带最终文本、没有绑定引文、校验却为 `PASS`。例如 Q007 的核心回答有材料支撑，但使用了圆括号。当前产品已经将这类结果显示为部分完成，并告知缺少可打开的引文。读取底层 PASS 统计引用成功率仍会高估交付质量。另有 Q060 说明即便合法编号存在，原句也可能不足以证明“这两个人就是同一人”。[编号提取与发布](../../src/genshin_corpus/rag/clean_research.py#L619) · [编号验证](../../src/genshin_corpus/generation/clean_evidence.py#L233) · [产品对无引用的提示](../../frontend/src/components/MessageItem.vue#L50)

**建议验收。** 分别报告“识别出的编号均有效”“至少一个可打开的引文”“重要断言获原文支持”。测试全角括号、错误编号、混用格式及合理的无证据答复。能唯一对应本轮已交付编号的格式可考虑归一，有歧义时显示原样并提示缺口。语义支持另做原句复核。

### F10 · P2　两个历史恢复样例的逐题导出仍指向旧目录

G7 的 Q001、Q002 在总索引中指向各自的 `-recovery-r01` 目录，但 `records/Q001/result.json` 和 `records/Q002/result.json` 内的 `source_store` 仍是最初目录。用该字段拼接真实 `sources_ref.path`，两份文件均找不到。改用已对账的总索引后，两份均存在，本轮引文回查也成功。历史恢复已有专门更正记录，这个差异只影响从独立逐题导出进入的读者。[逐题导出示例](../../data/generation/g7-70q-baseline-20261117/records/Q001/result.json) · [对账记录](../../data/generation/g7-70q-baseline-20261117/recovery-index-reconciliation.json) · [G7 总索引](../../data/generation/g7-70q-baseline-20261117/index.jsonl)

**建议验收。** 新导出从同一处解析已封存的恢复目录，逐条按相对路径和哈希验证。对旧基线提供兼容读取或勘误映射。以总索引、独立逐题结果两个入口打开同一回答，应落到同一份来源记录。

## 下一步优化顺序

### 先让关键问题可以离线验收

1. **证据和连续对话。** 建议下一项工程工作先覆盖 F03、F06、F08。三者已有小夹具或历史回执，分别能检验“模型所见是否逐段能查”“纠正助手是否保住用户条件”“断在本地查询能否继续”。它们直接影响研究者能否信任一次查证。F07 的长消息准入可以一并纳入产品接口验收。
2. **采集更新。** F01、F02 应在下一份 Raw 快照采集前解决。范围判定需要由 Collector 输出，Clean 只验证是否满足所需输入。用现有夹具演练新旧两个 run、栏目无匹配、业务错包、缺失元数据及跨栏目重复，检查旧快照引用。这个工作与使用现快照开展问答评价可以分开安排。
3. **有限真实试用。** 当前阶段文档登记的下一项真实语义验收仍是另行开启有限批次。建议试用时固定快照、S0、重排器、模型配置与预算，先测现状。将 F04 的候选目录、F05 的父级查阅和 F09 的引用提示作为可分别比较的变化，避免三个环节一起改完后仍无法归因。[当前阶段及授权](../current-phase.md)

### 把评估单位从“整题答对”细化到“每个必要结论如何得到支持”

建议建立一组与历史 70 题独立的小样本。例如 24 道新单题可分为 8 道单点事实、8 道多实体或条件对照、4 道时序或叙述归属、4 道材料不足或题设有误。另加 6 组三轮对话，分别插入指代、局部纠正与重开。它是试验设计示例，实际规模由人工复核时间和有限批次预算决定。

先由审阅者只看问题和原文，标出必要子问、可接受的原句位置、条件与仍未知的事项，再看匿名化输出。有分歧时保留双方理由。找不到可靠原句时允许标为未知。用 Q046 一类已知题检查回归，用独立留出题评价新使用场景。[Q046 与 Q050 的离线对照](../research/clean-generation-g6-s0-sparse-offline-study-20261117.md)

| 所有路径绑定物理位置，还是分离资产身份与位置 | 长期可用性需要同时保住历史哈希和可恢复性。对共享语料/模型，可试验按内容身份解析本地位置。涉及历史付费许可和未决请求时，仍须按原操作核对。 | 在另一根目录恢复同一份数据，验证旧引文、版本差异、Mock 和本地查原文。判定恢复有效时，应能列明哪些内容已逐字节匹配，哪些授权需要重新取得。[本机数据与恢复](../local-chat.md) |
